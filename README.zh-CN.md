> 约束不该只活在提示词里，它应该在动作发生前被拦截。

Project-Amos（简称 AMOS）取自 **A**gent **M**andate & **O**versight **S**ystem。顾名思义，它关心的是“授权”与“监督”，而不是“智力”。我们不打算让模型变得更聪明，而是想办法让它的手脚更守规矩。

## 为什么做这件事？

今天，我们对 Agent 的绝大多数行为约束，依然是写在 `AGENTS.md`、系统提示词或项目文档里的自然语言。用大白话告诉模型“你应该做什么”很方便，但指望靠这几句话在关键时刻拦住危险动作，本质上是在赌运气。这种做法有三个绕不开的硬伤：

1. **全凭模型自觉**：听不听话是个概率问题，永远成不了工程保证；
2. **注意力稀释**：规矩立得越多，单条规矩就越容易被当成耳旁风（也就是经典的 Lost-in-the-Middle 现象）；
3. **上下文压缩丢失**：当对话太长、上下文塞不下时，总得删掉点什么——但到底该删哪条规矩，根本没有安全判据。

Amos 的思路很简单：把约束从“口头提醒”升级为“物理机制”。模型只管提出动作申请（propose），到底能不能干，由底层运行环境在动作产生真实副作用之前做出确定性裁决（dispose）。硬边界交给策略引擎死守，软性的编码偏好才放进上下文里。

### 核心主张

- **模型提议，系统裁决（Proposer vs. Disposer）。** 每一个动作在落地前都必须过一遍确定性策略引擎。只要引擎说“不”，模型编出花来也无法推翻裁决。
- **硬规则必须有确定性的命中条件（`predicate`）。** 自然语言写成的说明（`narrative`）只是给人看、给提示词用的参考视图。如果一条规矩实在写不出确定性的机器判断条件，那就老老实实标为 `advisory_only`（仅建议），绝不硬凑。
- **约束表是唯一的核心数据结构。** 策略引擎赋予它执行语义，Git 记录它的演进历史，而治理流程则严格把控它的写入权限。
- **“激活”与“注入”彻底解耦。** 从“全局规则库”到“项目激活集”，再到“当前任务注入集”，各司其职。激活决定了哪些规矩对当前项目有效；注入只决定模型这一秒需要看到哪几条提醒。**一条硬规则会不会被强制执行，跟它有没有被塞进当前的 prompt 毫无关系。**
- **规则从真实证据中“编译”而来。** 每一条规则都必须绑定明确的威胁模型、事故报告或探针（probe）测试结果。如果哪天背后的证据失效了，规则就该进入待复审状态，而不是像僵尸一样永远留在表里。
- **Agent 可以打报告申请改表，但绝不能自己动手。** 修改约束表本身就是一个受监管的高危动作；任何试图触碰 0 层（核心安全底线）的请求，都会被直接物理拒绝。
- **死守边界，不赌注意力。** 我们不做模型微调，不搞注意力蒸馏，更不会把系统安全寄托在“把提示词加粗、加感叹号”这种玄学上。

### 硬约束 vs. 软约束

| 维度 | 硬约束 (Hard Constraints) | 软约束 (Soft Constraints) |
| --- | --- | --- |
| **承载方式** | `predicate` + `on_hit` | `narrative` |
| **执行者** | 策略引擎 | Prompt 上下文 |
| **生效时机** | 动作产生副作用**之前** | 模型阅读上下文时 |
| **失效兜底** | Fail-closed（默认拒绝） | 模型可能会忽略 |
| **治理方式** | 0 层不可触碰；其余改动走提案审批 | 按项目与当前任务动态路由 |

### 它和 AGENTS.md 是什么关系？

不是取代，而是**投影**。怎么构建项目、怎么跑测试这类工程知识，依然留在 `AGENTS.md` 里；而约束表中的自然语言说明（`narrative`），会按维度自动渲染并更新到 `AGENTS.md` 的约束章节中。如果你把绝对不能踩的红线只写在 `AGENTS.md` 里，那就等于把安全交给了模型的自觉性——这在工程上是一种范畴错误。

## 它是怎么运转的？

下面展示的是系统的完整目标架构。目前所处的**阶段 A** 仅开启了“旁路观察”模式：引擎会照常跑完所有裁决逻辑，但结果只写进日志，还不会真正拦下任何工具调用。

### 一个动作的生命周期

```text
模型提议执行某个动作 (Action)
       │
       ▼
拦截器：将请求归一化为标准信封 (tool, operation, target)
       │
       ▼
策略引擎：读取项目激活快照 → 匹配命中条件 (predicate) → 合并裁决结果
       │
       ├─ deny    → 阻断副作用，记入审计日志
       ├─ confirm → 弹出结构化摘要，挂起并等待人工确认
       ├─ log     → 先放行，但记下“如果动真格会怎样”
       └─ allow   → 正常放行
       │
       ▼
Harness / 沙箱执行 → 追加写入 JSONL 原始审计日志
```

有一个关键细节：**拦截器只看结构化信封，绝不读取自由文本。** 这意味着路由和裁决天然免疫常见的提示词注入（Prompt Injection）——攻击者要想操纵路由，除非能篡改底层工具名，而工具名是由运行环境的解析器死死攥在手里的。

### 规则长什么样？

每条规则至少由三部分组成：

- `predicate`：供引擎执行的确定性**命中条件**（代码中保留 `predicate` 字段名，中文语境下统一称为“命中条件”）；
- `on_hit`：命中后的处理动作（`deny` / `confirm` / `log`）；
- `narrative`：写给人看、也喂给模型看的自然语言说明。

在 G0 阶段，我们冻结了 7 个基础命中条件操作符：`op_in`、`target_glob`、`target_outside_glob`、`url_query_key_in`、`target_scheme_in`、`target_host_in` 和 `target_host_not_in`。这里没有变量、没有脚本、没有复杂的嵌套布尔表达式，甚至连正则和自由文本匹配都没有。如果某个状态无法用这 7 个操作符表达清楚，那就坦然标为 `advisory_only`，绝不靠去猜 `target` 里的文本内容来硬凑逻辑。

### 三个集合，边界分明

| 集合名称 | 决定了什么 | 由谁消费 |
| --- | --- | --- |
| **全局规则库** | 系统里一共沉淀了哪些候选规则 | 治理流程与项目激活 |
| **项目激活集** | 哪些规则在当前项目里真正生效 | 策略引擎与 `narrative` 路由 |
| **当前任务注入集** | 此时此刻该提醒模型注意哪几条软约束 | Prompt 上下文 |

请记住：**只要一条硬规则在“项目激活集”里，无论它有没有进入“当前任务注入集”，引擎都会照单全收、严格执行。** 动态注入只是为了给上下文降噪，绝不会缩小安全防线的覆盖面。

在激活粒度上，系统支持按规则级别的 tags 或 `exclude_rules` 精细控制，而不是粗暴地按维度一刀切。启用新规则属于“收紧”，可以自动生效；但停用或排除已有规则属于“放宽”，必须经过人工点头。万一环境检测失败，系统会稳稳退回上一个有效的激活快照，绝不擅自关闭防护。

### 多个规则同时命中怎么办？

- **优先级排序**：`deny > confirm > log > allow`；
- **同级冲突**：一律以更严格的 `deny` 为准；
- **异常兜底**：遇到非法输入、未知操作符、解析失败或引擎内部错误时，无条件触发 `deny`（Fail-closed）。

### 规则治理：只收提案，不开放直接写入

修改规则表本身，走的也是和普通动作一模一样的监管管道：

- **新增 / 收紧规则**：自动生效，但强制绑定过期时间（TTL），且全程 Git 留痕；
- **放宽 / 删除 / 降级**：生成结构化的 Diff 摘要，必须等人类审批通过后才能落盘；
- **试图染指 0 层规则**：直接物理拒绝并记入越权日志，只要试探一次，当场吊销该会话的改表提议权；
- **TTL 到期**：自动回滚（Revert），不发提醒、不支持自动续期。

值得一提的是，Agent 在提案里写的“申请理由”**绝对不会**作为自动审批的依据——因为那段话本身就可能是被注入攻击污染的产物。无论是 `confirm` 弹窗还是审批界面，呈现在人类面前的只有冷冰冰的结构化摘要（工具、参数、目标、命中规则），绝不展示模型用来求情的小作文。

### 事实源、快照与日志

- **YAML 是规则的唯一事实源。** 在加载阶段通过 JSON Schema 和封闭词表做严格校验，保证规则文件本身人类可读、方便 Diff、易于 Code Review。
- **JSONL 是原始审计日志的唯一事实源。** 只追加、不修改（Append-only）。抽样样本和人工审核表都可以从它随时重建，但绝不允许任何流程反过来篡改原始日志。
- **SQLite 只是阶段 D 引入的派生读模型。** 它可以随时删掉重建，且**永远不会进入裁决热路径**——引擎在热路径上只读取深度冻结（Deeply Frozen）的内存快照。
- **快照加载失败时保留最后一次正常版本。** 配置改坏了不会把运行中的系统拖入半残废状态；如果是冷启动首次加载就失败，则直接按 Fail-closed 逻辑拦截并记录。

### 冷启动路线图：为什么不一步到位？

1. **Log-only（旁路记录）**：只记录“如果动真格会怎么判”，在真实任务流里跑一阵子，把误杀（False Positives）先抓出来；
2. **选择性强制**：只对最底线的 0 层规则开启真实 `deny`；
3. **引入人工确认（Confirm）**：把具有不可逆副作用的操作纳入人工确认流；
4. **治理闭环上线**：启用提案队列、TTL 自动过期与 Git 治理。

在安全领域，跳过冷启动直接全量拦截，结局往往是一场“拒绝风暴（Deny Storm）”——然后被逼疯的用户就会顺手把整个安全系统关掉。**一个会被用户嫌烦而关掉的安全系统，比没有系统更危险。**

在首批落地的 15 条规则中，有 10 条具备确定性命中条件（deterministic），5 条为纯建议（`advisory_only`）；如果按声明的 `on_hit` 动作划分，包含 11 条 `deny`、3 条 `confirm` 和 1 条 `log`（注：`advisory_only` 规则不会进入硬裁决流程）。每一条规则都标注了明确的 `source` 来源和极具诱惑力的违规测试场景（`probe`）——它们最初都源于一个个真实的威胁场景，随后才被逐步打磨成机器可执行的判断条件。

在接入层，OpenCode 适配器目前接管了文件类通道：`read` 映射为 `file_read`，`write` / `edit` 映射为 `file_write`，`glob` / `grep` 映射为 `file_search`，`list` 映射为 `file_list`。Pi 适配器除了覆盖对应的文件操作外，还会将 `bash` / `user_bash` 记录为 `shell_input`（出于隐私与安全考虑，不记录具体命令文本）。所有目标路径都会被解析为绝对路径（包括展开 `~`）；如果路径里还残留着未折叠的 `.`、`..` 或 `//`，引擎会直接按异常拒绝，而不会当成“未命中”糊弄过去。整个过程不读取、也不记录任何文件内容；遇到未知 Payload 或解析失败都会显式留痕。两个适配器的 Hook 目前都保持绝对克制：不篡改输入、不向上游返回裁决、不阻断任何工具调用。像 `http_request` 这类网络规则已经在引擎和测试用例中就绪，但还没挂载到实时 Hook 上；OpenCode 暂时跳过了 Shell 通道，且两边的 Patch 操作目前都还无法做结构化拆解。

人工审核工作表（Review Worksheet）直接从原始 JSONL 日志派生，抽样策略很明确：0 层命中全量提取、非 0 层的 `deny` 全量提取、各类错误与覆盖缺口全量提取，而 `confirm` 记录则优先按工具和规则覆盖度进行抽样。当前生成的工作表样本基于 158 条真实记录（包含 1 条 0 层命中、0 条非 0 层 deny、35 条错误/缺口，以及从 65 条 confirm 中抽出的 20 条）。生成工具只负责拉出待审队列，绝不越俎代庖去判断是不是误杀；同时为了保护人类劳动成果，它拒绝覆盖任何已经写有人工结论的文件。

**当前尚未启用的功能**：真实的 deny / confirm 拦截、OpenCode 的 Shell 通道与两边的 Patch 解析、项目激活快照与 `narrative` 动态路由、提案审批队列、TTL 自动清理、SQLite 读模型、本地 Web 治理台，以及自动化探针执行与违规率/误杀率仪表盘。Pi 适配器也还差一份真实的 CLI 运行样本。

G0（Go/No-Go）阶段门禁定于 **2026-10-30** 由人工逐项核验，目前状态为**未裁决**——在这件事上，Agent 没有给自己放行的权力。具体核验标准可查阅 [docs/go-no-go.md](docs/go-no-go.md)。

## 设计灵感从何而来？

最初的几条核心约束，诞生于设计 Termcp 威胁模型时的头脑风暴：我们先列出“Agent 干出什么事会让人彻底崩溃”，把它们写成具体的威胁场景，再反推提炼出机器能看懂的命中条件。

### 1. llm-wiki：把约束当成“编译产物”

Karpathy 提出的 `llm-wiki` 理念，是这套架构最直接的哲学源头。两者的核心设计原则几乎是一一对应的：

| llm-wiki 核心理念 | Project-Amos 的对应实践 |
| --- | --- |
| **原子化 (Atomic)** | 每一条规则都是独立、完整的最小治理单元 |
| **数据驱动 (Data-driven)** | 规则从威胁模型、事故和探针测试中“编译”产生，不靠拍脑袋凭直觉写 |
| **显式溯源 (Grounding)** | `source` 是必填的硬性引用，不是可有可无的注释装饰 |
| **无损演进 (Non-destructive)** | 改表全部走 ADD/FIX 提案，Git 留存完整轨迹，TTL 本质上是带保质期的 ADD |
| **晋升管道 (Promotion)** | 灵感想法 → 实验性规则（TTL + log-only）→ 探针实证 → 正式进入强制层 |

不过，结合安全场景的特殊性，我们做了两点关键修正：第一，执行引擎不直接去追那个随时在变的“活文档（Living Wiki）”，而是加载固定版本的项目激活快照（类似 `package-lock.json` 的语义）；第二，一条规则能不能转正，靠的是探针（Probe）跑出来的客观数据，而不是靠大家开会投票。用一句话来总结：**llm-wiki 存的是事实（Facts），而 Amos 存的是规范（Norms）。**

### 2. obelisk：读写分离的镜像架构

[tommy0103/obelisk](https://github.com/tommy0103/obelisk) 是一个优秀的 Agent 历史会话检索层：它把不同编程 Agent 产生的 JSONL 会话日志归一化后存进同一个数据库，给 Agent 提供 CLI 查询，给人类提供可视化浏览界面。如果说 **obelisk 管的是“Agent 记得什么”，那么 Amos 管的就是“Agent 不许做什么”**——它们恰好构成了同一套治理架构的读侧与写侧。

我们从 obelisk 借鉴了这些扎实的设计模式：

- **单库归一化 + 双受众界面（Dual Audience）**：Agent 用命令行高效查询，人类用图形界面从容审计；
- **多源异构投影**：把不同运行环境的事件投影进同一个标准信封（比如 OpenCode 和 Pi 各自将事件归一化），而不是去造一个包罗万象的通用 Agent 框架；
- **提案管线原型**：记忆层里“Agent 提议 → 人类批准 → 登记入库 → 日后召回”的闭环，几乎就是规则提案管线的天然模板；
- **分层的读取接口**：日常使用优先调类型安全的辅助函数（Typed Helpers），底层保留 Raw 查询作为应急逃生舱。

同时，我们也划定了明确的边界，清楚哪些东西**绝对不能照搬**：

- **绝不在热路径查数据库**：读历史记录慢一点、偶尔报错都没关系；但在安全裁决热路径上，一旦数据库损坏，配合 Fail-closed 策略就会瞬间演变成全舰队停摆（DoS）；
- **绝不在裁决侧开放任意 JS 查询**：灵活的查询接口只能留在事后审计和读模型里，裁决引擎必须保持封闭与纯粹；
- **不做 Electron 桌面端**：人类治理台只做轻量级的本地 Web 服务，而且绝不在第一天就抢着画界面——UI 只是状态的投影，得先有稳固的状态，再去谈界面；
- **严格规避 AGPL 许可证污染**：我们只参考其公开的 README、文档与架构决策记录（ADR），所有代码通过净室（Clean-room）方式从零重写，确保规范与一致性测试套件从第一天起就保持宽松开源许可。

### 3. Jev：永远只坐“顾问席”

Jev（TypeSafe AI 的 System One 快速决策模型）在系统里只允许出现在四个纯粹的**辅助顾问（Advisory）**位置上：语义路由、提案预分类、探针评估（Jev-as-a-Judge），以及将自然语言意图映射为命中条件模板。它**永远不进策略引擎、永远不拥有审批权、永远碰不到 0 层规则**。模型的置信度（`confidence`）不等于系统的授权（`permission`）——任何可解释性不足的黑盒模型，都没有资格坐上最终的裁决席。

### 4. 其他工程参照

- **iptables / 防火墙语义**：软约束（`narrative`）路由只检查结构化信封，采用“精确匹配 + Glob 通配”并遵循精确度优先原则；如果没匹配上，则 Fail-open 回退到当前项目激活的全部软约束。你可以直接把它理解成 **“面向提示词说明的 iptables”**。
- **Lost-in-the-Middle（Liu et al., 2023）**：实证研究表明，塞进上下文的规则越多、位置越靠中间，模型就越容易视而不见。这篇论文恰恰是我们坚持“动态按需注入”以及“激活与注入分离”的理论依据——当然，它更是我们拒绝把安全底线交由 Prompt 负责的原因。
- **AGENTS.md 规范**：把“工作约定”和“强制机制”彻底分开。`AGENTS.md` 依然是项目工程知识的最佳入口，而其中的安全与行为约束章节，则会变成由 Amos 规则表自动生成的派生视图。

## 快速上手

环境要求：Node.js 26、npm。如果你需要实际挂载运行适配器，还需安装对应的 OpenCode V2 或 Pi 环境。

```bash
npm ci
npm run build
npm test
npm run typecheck
```

注：`npm test` 会自动先执行编译构建，随后运行编译出的 JavaScript 测试套件。

### 在 OpenCode V2 中以 log-only 模式体验

```bash
npm run build
```

项目根目录下的 `opencode.jsonc` 已经配置好从 `dist/adapters/opencode-v2/` 加载插件，并显式传入了规则表、Schema、日志输出路径以及 `log-only` 运行模式。构建完成后，直接在这个目录下启动 OpenCode V2 即可。插件会在后台默默记录“假如强制执行会发生什么”，不会打断你的任何正常工具调用；实时审计日志会写入 `spike/logs/opencode.jsonl`（已被 Git 忽略）。

Pi 适配器的代码位于 `adapters/pi/`，同样默认运行在安全的 `log-only` 模式下。

### 生成人工审核工作表

```bash
npm run audit:review -- \
  --rules constraints/rules.yaml \
  --log spike/logs/opencode.jsonl \
  --output spike/review/new-review.md
```

注意：`--output` 指定的必须是一个尚不存在的新文件路径，这是为了防止手滑覆盖掉你已经填好的审核结论。如果你有多份历史归档日志，可以通过重复传入 `--log` 参数一并汇总分析。

## 系统边界与演进阶段

当前我们聚焦于打磨**单机、单信任根**的最小治理闭环，服务于个人开发者与封闭受控的 Agent 舰队。至于多端同步、团队协作（包括云端托管或云辅助形态），属于后续的演进方向，不在当前阶段的交付范围内。

四个演进阶段的门禁划分：

- **阶段 A（当前）**：跑通 `log-only` 旁路模式，采集真实任务日志，完成首轮误杀（False Positive）人工审核。
- **阶段 B**：对 0 层核心底线开启选择性强制拦截（`deny`），随后引入高危动作的人工确认流（`confirm`）。
- **阶段 C**：上线规则提案队列、人工审批流、Git 审计溯源与 TTL 自动过期机制。
- **阶段 D**：构建 SQLite 派生读模型，并提供轻量级的本地 Web 治理控制台。

在当前阶段，我们只交付 OpenCode V2 与 Pi 两个 `log-only` 适配器。以下方向明确**不在计划内**：提示词工程类的软约束调优、接入第三个运行环境（Harness）、让大模型参与安全裁决、发明自定义命中条件 DSL、支持正则表达式路由，或者搞所谓的“规则交易市场”。最后，一条铁律：**绝不为了追求架构上的形式美感，去妥协 `deny > confirm > log > allow` 的裁决优先级、同级冲突取 deny 的原则，以及 Fail-closed 的安全底线。**
