# Amos 产品设计：一个激活集，拦截与注入两个投影

状态：**目标设计，2026-11-02 修订；不是已实现能力清单。** 本轮只更新设计和文档，不迁移配置、不启用安全强制执行。当前实现与十一项差距的证据、实施顺序和验收见 [差距闭环](product-gap-plan.md)。安全运行期仍为 **NO-GO**。

> **2026-11-05 实现补充**：限定范围 Harness 层 MVP 已交付并验证：Vue 控制台发布 P1 项目快照，真实 Pi `managed` 会话消费同一快照执行 deny/confirm/allow，confirm 经独立 reviewer + 一次性授权，advisory 同源注入，并写 runtime 报告供控制台读取。它不是 OS 沙箱，默认仍 log-only；完整范围与证据见 [MVP 交付](mvp-delivery.md)。

## 1. 产品承诺与边界

产品始终是三块，缺一不可：

1. **Approve for me**：宿主先限制执行，`on-request` 先停住需要审批的动作，独立 Jev 安全审查角色只处理这一次请求；日常放行不等待人逐次审阅。
2. **内置标准 + 用户自定义多维拦截规则**：人可编辑维度、适用性、命中条件、处置和生命周期；硬拒绝不能被审查者推翻。
3. **工程规范动态注入**：按区域、路径和任务提醒模型；与硬规则来自同一项目激活集，但不拥有执行或批准权。

工程 Shell 护栏保留；已经实现的 Jev 工程审查与要求一致性仍然只能收紧，不复用为安全批准器。治理服务、SQLite 和 GUI 是这三块共用的管理支撑，不是第四个产品。

**最新目标：人维护多维规则、安全边界、架构与工程标准，不逐次审批门禁。** 动作、工程完成/接纳和 rollout 晋升均由系统在已批准规则与范围内，以确定性检查、真实证据和适用时独立 Jev 审查作决定；模型不是硬拒绝或失败检查的覆盖开关。自动晋升必须有可信、版本绑定的机器可验证证据和预先制定的通过标准，不能只凭模型摘要。缺证据、超时、低置信度或不支持时保持停止，而不是悄悄放行或转成人工个案审批。人可修改规则及预授权、排查故障或停机；这些是治理，不是正常路径的逐次放行。Jev 可能误判，系统自动化不等于安全保证。

**GUI 阶段的配置唯一事实源是受保护服务持有的 SQLite。** Git 不再是配置发布前提；YAML、JSON、Git 导出和 `AGENTS.md` 都不是第二个权威源。本条取代截图中“控制台只浏览和提案，修改走 Git”的目标，以及旧方案中“人直接编辑 YAML 作为长期日常入口”的安排。

## 2. 用户工作流

1. 人在 GUI 注册项目，选择内置标准和工程规范，查看语言/框架检测建议及逐规则激活差异。
2. 人确认初始配置；服务验证、保存不可变配置版本，并编译该项目的激活快照。检测结果不能冒充批准。
3. 宿主启动受管会话，验证快照来源及宿主能力；显示 `managed`、快照版本、有效规则和覆盖限制。普通插件会话仍显示 `observer` / `guardrail-only`，不冒充受管会话。
4. 模型在工作区内工作。所有受管执行入口先处理结构化动作；可执行规则全部评估，规范按任务动态注入。
5. 无硬拒绝的 confirm 类请求先停止，再交独立 Jev 安全审查角色；失败保持停止。重试由系统按有界策略重新校验和审查，不要求人逐次授权，不可绕过拒绝或反复尝试。
6. Agent 可以提案。可信发布器只自动接受预授权范围内、可确定证明的临时收紧；放宽、删除、降级转人工。GUI 展示生效版本，不以“已保存草稿”冒充“已激活”。

## 3. 配置与信任架构

```text
人 → GUI → 已认证的治理 API → 校验/分档/发布 → SQLite（配置事实源）
Agent → 受限提案 API ────────────────────────┘
                                            │
                                  编译并认证项目激活快照
                                            │
                         ┌──────────────────┴──────────────────┐
                         ▼                                     ▼
                   宿主/执行中介                          Injector
            结构化动作 → 确定性评估                 同一快照的 narrative 投影
               deny / confirm / log                     路由、去重、预算
                         │                                     │
                已停止的 confirm → 独立审查者                   模型上下文
                         │
               单次授权核验 → 受限执行器
                         │
                  受保护审计写入端
```

- SQLite 只能由受保护服务打开。Agent 不得拿到数据库文件、WAL/SHM、备份、发布密钥、激活指针或人侧认证凭据的写权限。GUI 通过类型化 API 修改配置，不直连数据库，不执行任意 SQL。
- 隔离靠独立 OS 身份、受限进程/挂载域或等效的宿主信任边界；换目录、同用户 `0600`、签名文件或“本地服务”本身都不足以成立。被攻破的宿主、服务和人侧信任根不在本保护范围内。
- 引擎只读不可变内存投影，**不查 SQLite，不访问文件系统，不运行模型或分析器**。后台服务负责存储、发现、编译与发布。
- 人侧配置 API 与 Agent 提案 API 权限分离。现有本地治理控制台已实现分离令牌与角色权限、防 CSRF、Host/Origin 校验及不可信内容安全渲染；这些是本地应用防护，不阻止同 UID Agent 访问令牌或数据库。目标受保护服务仍须在真实隔离身份下验证最小权限、配置发布与宿主接收边界，不能据此宣称可信隔离或自动治理已完成。

### 3.1 “全部配置入 SQLite”的清单

| 配置域 | SQLite 中的权威内容 | 文件/外部系统的剩余角色 |
|---|---|---|
| 规则与内置标准 | 标准包版本、规则版本、七算子命中条件、narrative、来源引用 | `constraints/rules.yaml` 是迁移输入、fixture 和导入/导出格式 |
| 项目与会话策略 | 项目标识、受信工作区绑定、tags、逐条激活/排除、默认包、会话配置版本 | 项目清单和源码只提供不可信检测信号 |
| 工程规范与注入 | 规范版本、路由、baseline、配对、优先级、预算、渲染配置 | `guidance/packs.ts` 是迁移种子；`AGENTS.md` 是带版本的派生视图 |
| 工程护栏 | 启用项、封闭 Shell 策略配置、固定检查配置、完成审查设置 | 检查器/lexer 是可信代码，不变成数据库里的可执行脚本 |
| 宿主与安全审查 | 沙箱配置、可升级请求的上限、审查者/provider/model allowlist、超时、出境同意策略 | 宿主原生配置是受保护的生成投影；不声称 harness 可以直接读 SQLite |
| 生命周期 | rollout 状态、probe 定义及证据引用、TTL、自动收紧预授权、配额、审批记录 | 测试代码、编译器及版本化 Schema 仍随软件发布，不当作可编辑配置 |
| 连接与运维 | provider 地址、凭据引用、审计保留策略、导出/备份设置、GUI 偏好 | 凭据材料在 OS secret store 或隔离的秘密存储，不以明文配置入库 |

`opencode.jsonc` 的 Amos options、`.pi/amos.json`、`decision/jev.local.json` 中的非秘密配置都在迁移范围内。Amos 不接管宿主应用的其他配置。宿主仍需要的安装声明、连接入口和原生权限文件由服务生成；手改投影不能反向写库或扩大权限。

仅保留不可避免的**启动引导**：如何定位受保护服务/数据库，以及获取人侧认证/秘密存储的信任根。它由安装器或宿主部署管理，不是项目可改的安全开关；数据库损坏不能通过“回退到项目 YAML”启动受管执行。CLI 若保留，只是相同 API 的客户端，不形成另一套配置。

### 3.2 逻辑记录与发布事务

以下为待实现的逻辑契约，不是当前 SQL Schema 或已冻结协议：

- `RuleVersion`：规则 ID、不可变版本、既有多维字段、narrative、来源；注入元数据按同一 ID/版本关联，不复制成第二份可独立编辑的规则。
- `ProjectConfigVersion`：项目绑定、标准包版本、逐条激活/排除、路由和配置引用、基于哪个前版本修改。
- `Proposal` / `Approval`：类型化 diff、提案者的可信通道身份、预期旧版本、TTL、证据、批准范围；理由文本不参与自动授权。
- `RolloutRecord` / `ProbeRun`：规则版本、执行入口、项目/环境范围、晋升状态及真实结果引用。
- `ActivationSnapshot`：不可变编译内容、来源认证、激活清单、各投影、版本及 digest。

发布必须以旧版本 CAS 检查、审批校验、记录追加和发布意图在事务中提交。编译产物在事务外准备、核验后原子替换激活指针；失败不出现“半份 enforcement + 半份 advisory”。发布到数据库不等于宿主已接收，须单独记录分发/接收回执。Git 导出失败不能变更生效策略；备份恢复和旧版本回滚都需要新的认证发布，不能把旧指针文件放回去。

## 4. 全局库、项目激活集、任务注入集

### 4.1 唯一的激活计算

设 `L` 为已发布规则库，`B` 为不可被项目排除的标准基线，`P` 为批准的项目选择，`Tₑ` 为未到期的临时收紧：

```text
Aₑ = mandatory(B) ∪ approvedSelection(L, P) ∪ Tₑ
```

激活单位是 **rule ID + version**，不是维度开关。`dimension` 是分类标签，tags/语言/框架是适用性输入，不能代替授权。`exclude_rules` 仅作用于可排除条目；排除必选基线或削弱标准 0 层拒绝，编译直接失败。基线是显式激活成员，不是偷偷在激活集外执行的另一张表。宿主沙箱另属于基础设施，不是可停用的规则。

检测只产出带输入 digest 的建议。移除 `pyproject.toml`、改项目类型、检测报错，均不能自动移除已有激活项。无法核验项目身份或首次没有有效快照时，不开启受管执行；替换失败保留最后有效快照，但不延长已到期规则或已撤销授权的寿命。

### 4.2 同源，不是同一 payload

同一 `ActivationSnapshot` 编译出：

- `runtime` / `ci` / `server` 投影：当前激活的可执行规则，按已批准 rollout 状态分为实拦和 shadow 评估。所有适用硬规则都评估，不受任务路由/提示词/注入预算筛选。CI/server 投影只能在相应真实检查点宣称强制。
- `advisory` 投影：激活条目的 narrative，包括纯 advisory 和硬规则的解释；它不含裁决权。

因此**同一条硬规则可被执行，也可被解释给模型**。现有 `enforcement` 仍描述执行机制，不改成两个互斥产品；不要求把硬规则改成 `advisory_only` 才能提醒。纯 advisory 永远没有硬裁决。投影必须绑定同一激活 digest、rule version 和 epoch，配对不可由调用方自报已激活。

两个集合不必数量相等，但来源必须相同：未激活规则**既不评估，也不新注入**；没有选入本轮上下文的硬规则仍照常评估。注入器只读，不能写回激活集或放宽执行。

### 4.3 会话固定与临时收紧

- 会话的批准基版、宿主权限和编译器版本固定。普通配置编辑、放宽和基线升级只对以后会话生效。
- 唯一允许的中途规则变化，是受信发布器在预授权内发布的**附加型临时收紧层**。每次新增/到期产生新的不可变 epoch，两个投影原子切换；不是 Agent 热改旧快照。
- 每个动作捕获一个 epoch；异步审查后、实际执行前必须再次核验有效 epoch 与 TTL。epoch 已改变则旧批准失效，重新裁决，不沿用较松结果。
- TTL 到期自动退出临时层是预授权生命周期结束，不是一次可被 Agent 发起的任意放宽。到期不依赖清理器运行，不自动续期；清理器只整理记录。时钟倒退/无法验证到期状态时暂停受管执行并要求恢复，不能重启后重新计算 TTL。
- 不支持 epoch 原子切换的宿主只能在下次会话接收收紧，必须申报这一限制；不能宣称运行中自动生效。

建议快照身份绑定 `format_version`、规则/标准包版本、Schema/编译器版本、项目身份与有效工作区、宿主 envelope、激活/排除、rollout、路由/预算、基版、epoch、临时层到期时间和所有投影 digest。digest 是内容标识，不是来源认证；来源另由受保护发布清单/签名等机制核验。

合法的空 CI/advisory 投影与“快照缺失、编译失败”须有不同的显式状态；不能把错误转换成空集后继续。当前 engine 拒绝空规则数组，未来编排器不能靠调用 `evaluate(action, [])` 表示合法空检查点，也不能修改该 fail-closed 语义。

## 5. 执行、沙箱与一次批准

1. 受信宿主构造完整动作信封；Agent 提交的 `approved: true`、项目身份或规则版本没有认证效力。现有引擎只接收 `{tool, operation, target}`；会话身份、执行能力和审批信息在外层绑定，不能偷偷塞进严格的旧 action。
2. 宿主先拒绝未知执行器、结构错误、受保护路径及不可升级的操作。已识别动作才进入确定性规则评估；封闭 Shell 护栏继续运行，未知语法不变成 allow。
3. 任一确定性 `deny` 都停止，**包括非 0 层 deny**；没有安全审查席位。`confirm` 或可升级的沙箱越界先停止，产生一个请求。
4. 安全审查者仅判断这个已停止请求。人侧预先批准的宿主“可升级上限”决定哪些例外能被请求；没有相应受限执行器时，不给审查者虚构一个执行能力。
5. 审查通过后，宿主消费绑定动作摘要、快照/epoch、session、有效期和 nonce 的一次授权，并在执行前重检。拒绝、超时、拒答、低置信度、校验错误、审计不可用均不执行。

默认工作区可写、网络关闭。批准**一次**允许范围内的外部文件操作或网络请求，不等于修改永久 writable roots 或全局开启网络。硬拒绝的凭据/策略/审计路径没有例外。首个执行器不提供任意“脱离沙箱运行 Shell”；绑定一段命令文本并不能证明其子进程只做一个副作用，无法限制的升级保持不支持。

安全审查状态至少区分 `pending`、`approved`、`denied`、`failed`、`timed_out`、`expired`、`cancelled`、`consumed`。一次授权不是执行成功回执；执行结果/未知结果另记。系统重试不能覆盖确定性 deny，且仍可被审查者拒绝。反复拒绝应终止当轮而不是让主 Agent 换入口继续尝试。

沙箱内已知、可执行、无命中的正常动作可继续；这是**目标宿主路径**的 allow 基线，不改写当前 log-only recorder 的 hypothetical no-match deny。宿主可以包含任意不可信项目脚本，Shell 分类器的“安全命令”标签并不能让它们脱离沙箱。

## 6. 语言语义规则与不可绕过检查点

Python/Rust/TypeScript 语义不靠路径、正则或模型猜测。受保护 runner 执行固定版本的 AST/编译器/linter；代码、构建脚本和解析器也在资源限制/无秘密的隔离域中运行。

发现信封至少绑定：runner 身份、analyzer/check 版本、规则版本、输入 tree/blob digest、项目、检查点、规范化文件/位置、结构化 check ID/结果、执行成功状态与覆盖范围。不把自由文本诊断当作真假；缺少成功信封不能解释为“零发现”。有结果也必须与当前待接受的代码版本一致，变更后旧结果不能复用。

**七个谓词操作符不扩展。** 当前三字段 action 无法表达 AST 事实，因此这类规则暂时保持 advisory 或单独的工程检查。后续用独立、严格版本化的 check-binding 清单，把已注册 check ID/失败事实映射到同一 rule ID 和检查点结果；不伪装成现有 `predicate` 已能消费 finding，不把 `finding.*` 作为第八个算子。映射/纯求值的扩展需专门 ADR 与兼容测试；执行分析器始终在引擎外。

该后续契约的最小形状为：

| 工件 | 固定职责 |
|---|---|
| `CheckBinding` | 关联 `ruleId/ruleVersion`、受信注册的 `checkId/checkVersion`、analyzer、检查点与覆盖要求；只引用已有规则的 `on_hit`，不藏第二份处置表达式 |
| `FindingBatch` | 绑定运行身份、输入 tree、版本和成功/失败状态，给出该检查覆盖内的类型化结果；成功且完整的零发现才算通过 |
| 纯检查求值 | 验证绑定、覆盖、版本和输入一致性后，把对应失败 check 归到激活 rule 的处置；所需信封缺失/失败/陈旧则检查点 fail-closed；不运行分析器或解释诊断文字 |

要把这类规则晋升为硬检查，必须显式发布支持 check-binding 的新规则/编译格式版本；旧 `advisory_only` 条目不能仅加一条映射就被悄悄变成硬规则。新格式区分 action-predicate、registered-check 与 advisory 条件来源，不混用两种信封；七算子继续只用于 action-predicate。当前 loader 仍拒绝这些新格式，后续 ADR 是实现/兼容审查门，不是允许在旧 Schema 里先塞字段。

本地 pre-commit 仅作快速反馈。若可绕过，真实接受点必须是受管宿主的提交/导出门或**受保护 CI 必需状态**；检查覆盖提交的精确 tree，Agent 不得删除要求或自行伪造成功。CI 只能阻止受保护分支接纳，不能追回此前文件写入/网络副作用，不借它宣称运行期拦截。仓库已有 CI 配置不等于远端保护已经配置完成。

## 7. Agent 提案、自动收紧与人工放宽

“Agent 没有写表权”与“收紧自动生效”通过**可信发布器**衔接，而不是给 Agent SQLite/Git 写权。

| 变化 | 发布规则 |
|---|---|
| 在人预授权范围内，激活已批准、已验证版本的非 0 层 deny/confirm 模板，保留全部旧规则 | 可自动发布临时附加层；必须有限 TTL、配额、来源证据、审计和对应 rollout 资格 |
| 新写规则/叙事、改命中条件、改变路由/预算、不能证明严格性的改动 | 提案待审；新规则从 log-only 开始，不因自称“收紧”就实拦或注入未经批准文字 |
| 停用/排除、删除、降级、缩小规则适用面、扩大宿主权限、续期/永久化 | 人工批准新的配置版本；只能以后会话采用，紧急人工停机不受此限 |
| 修改/排除标准 0 层拒绝或突破宿主硬保护 | 拒绝并审计；不进入安全审查者批准流程 |

初始自动化只做**追加独立限制**，不做任意规则的语义包含证明。glob 变窄对 deny 可能是放宽，对允许范围则可能是收紧，不能凭字符串 diff 分类。新增模板的实际保护不得因替换同 ID、清空旧集合或改变路由而减少。`owner: agent` 是提案来源，不是发布授权；该来源保留，可信发布记录另外绑定人的预授权。Agent 和安全审查者都不持有发布能力。

建议初始预授权默认关闭；人启用后默认 TTL 1 小时、单次上限 24 小时，项目活跃临时条目和频率设有限配额。这些是可配置的产品默认值、不是现有代码行为。TTL 自可信发布时开始；重复提案、重启和失败回退均不能延长。永久保留须人批准。TTL 不代替真实 probe，也不允许新规则跳过 rollout 晋升。

## 8. 动态上下文与工程护栏

内置规范与人编辑规范统一进规则库。硬规则保留 narrative 投影；纯规范保留 `advisory_only`。`guidance/packs.ts` 迁移后只剩初始化/测试种子，不能成为第二条运行期规则来源。

选取顺序：快照中已激活且未过期的 narrative → 受管路由/结构化区域与路径/任务标签 → prompt 辅助排序 → 去重和预算 → 独立的 advisory 块。prompt 不能激活、排除、持久 suppress 或修改规则。路由配置的 suppress/预算缩减也属于需要治理的防护减少。

路由失败时回退候选集是**项目全部激活 narrative**，不是全局库；渲染仍受预算限制，明确记录未呈现 ID、回退原因和 `incomplete`，不声称“全部规范已送达”。只有宿主确认接受后才记录注入成功。注入失败不能改变执行 verdict 或单次批准。

注入块与审计绑定 activation digest、epoch、advisory digest 和规则版本。临时规则过期后不得新注入；已经进入历史上下文的文本不能保证抹除，支持时替换受管区块，否则追加到期说明。旧文本从来不授予/撤销执行权。

工程 Shell 护栏、固定检查和 tighten-only Jev 保留。GUI 可管理其配置，但不能把护栏开关当成沙箱开关。当前普通插件仍按既有配置显式启用；迁移之前不改变它们的行为。

## 9. 审计、来源与恢复

- 审计写入者在 Agent 可写域之外，Agent 仅查询授权的脱敏视图。可以使用独立的受保护审计 SQLite；配置数据库和审计数据的保留/备份职责分别记录，不给浏览器和 Agent 任意写入口。
- 记录项目/session、可信通道身份、规则/激活/epoch、动作的不可替换绑定、shadow 与实际裁决、审批状态、执行回执、检测/发布/过期、注入接受和遗漏。审计不写文件内容、命令原文、URL 秘密值、用户要求原文或原始敌意 payload。
- 执行前须有持久授权审计回执；写入失败停止，不像当前观察器那样吞错继续。执行后补结果；崩溃留下 `outcome_unknown`，不得重放为“已批准但未执行所以再执行一次”。分库不能假装自动拥有跨库事务。
- 同域 hash 链/SQLite 不提供外部防篡改。要声称可检测被攻破服务后的历史重写，需外部锚定/独立留存。没有该部署证据就只声明“对受监督 Agent 不可写”。
- 恢复时验证配置版本、发布来源、激活指针和剩余 TTL；坏迁移、未知 Schema、缺少标准包、撤销/过期状态不明时不能降级为项目文件模式。最后正常快照回退不等于可以永远运行陈旧授权。

## 10. 迁移与兼容策略

1. **现在**保留 YAML/JSON 配置和 log-only 管道，先完成项目激活的离线编译与双投影一致性验证；不为此接入旧治理台写权限。
2. **GUI 交付阶段**由人显式导入现有配置（含 guidance 和 Jev 非秘密配置），预览完整差异；检查严格 Schema、重复 ID、来源、秘密引用和未支持字段。缺失不能默默取默认或丢失。
3. 用事务导入为不可变版本，先编译候选并做兼容/故障测试，再认证发布、取得宿主接收回执。切换后 SQLite 单主；旧配置文件只读并标明迁移版本，不参与自动 fallback 或双向同步。
4. 当前快照 archive v1 的 digest 算法和 JSONL v2 不重写。新激活/审计格式显式升版并关联 legacy digest；旧日志按旧解析器读取，不补写虚构激活或审批证据。当前严格 rule Schema 不新增 `tags`、`rollout`、`findings` 等未支持字段；迁移元数据用独立版本化记录承载。
5. 发布失败留住最后有效版本；schema 升级先做带 WAL 一致性处理的备份/恢复演练。回退是服务认证的版本操作，不让 Agent 自选旧数据库或旧导出文件。

GUI/SQLite 不先于可验证的宿主边界冒充安全能力；可独立演示配置管理，但必须显示“未接管执行”。下一份运行代码 PR 只做一个可运行切片，顺序与通过线见 [差距闭环](product-gap-plan.md)。

## 11. Codex 接入与适配能力

优先复用已提供沙箱和单次审批的宿主，而不是在其中再造一层假沙箱。Codex 的官方 [权限与安全](https://learn.chatgpt.com/docs/agent-approvals-security) 和 [Auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review)（2026-11-02 核对）说明：`workspace-write`、`on-request`、`approvals_reviewer = "auto_review"` 保留原沙箱，审查已需要审批的动作，不对日常动作逐一审查。

Amos SQLite 配置只能编译为宿主**实际支持**的受保护原生配置/规则或受管中介输入。不是所有七算子、多维规则、动态注入生命周期都能映射成 Codex 命令前缀或一个 hook；无法无损映射必须报 unsupported 并拒绝宣称该项强制。用户目录不是天然 Agent 不可写，仍要核验实际 sandbox/managed requirements。

`SessionStart`、`PreToolUse`、`PermissionRequest` 等旧设计列举的具体接缝只是待锁定宿主版本的候选；须逐项查证 API、阻断/失败语义、顺序和覆盖，再通过真实 probe。hook 失败放行的路径不能承载强制 deny。hosted web、MCP、浏览器、子进程/持久终端等分别申报覆盖，不能从“命令有沙箱”推导完整接管。Pi/OpenCode 的 NO-GO 不因另一宿主有能力而解除。
